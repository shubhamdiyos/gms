## 6. Risk Assessment

### 6.1 What Could Go Wrong Without Database Verification

1. **Transaction rollback not working** — The validate-all-before-write fix throws exceptions, but if `@Transactional` is not properly configured, partial commits could still occur.

2. **Concurrency issues** — Two teachers marking attendance for the same student simultaneously could bypass the application-level duplicate check and hit the database constraint, resulting in 500 errors instead of graceful handling.

3. **Cross-school data leakage** — A bug in tenant-scoped queries could allow school A to mark attendance for school B's students.

4. **Constraint violation handling** — The application might not properly handle `DataIntegrityViolationException`, resulting in 500 errors instead of user-friendly messages.

### 6.2 Mitigation

- R4.2 unit tests verify the code path (exceptions before writes)
- Database constraint `uq_attendance_student_slot_date` exists and will reject duplicates
- Tenant-scoped repository methods prevent cross-school access at the query level
- `GlobalExceptionHandler` maps `DataIntegrityViolationException` to 409 Conflict

**Residual Risk:** MEDIUM — Transaction behavior and concurrency not verified against real database.
