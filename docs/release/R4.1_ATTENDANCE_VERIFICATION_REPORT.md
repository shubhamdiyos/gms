## Phase C — ATT-06 Retry Behavior Documentation

### Transaction Behavior

**@Transactional annotation:** `AttendanceServiceImpl.recordBulkAttendance()` is annotated with `@Transactional` (line 105), which means:
- All operations within the method execute in a single database transaction
- If any exception is thrown, the entire transaction rolls back
- Partial records are never committed

### Scenario 1: Rollback on Failure

**Behavior:**
- If an exception occurs during the loop (e.g., student not found, classroom mismatch), the method throws an exception
- Spring's transaction manager rolls back the entire transaction
- No partial attendance records remain in the database
- Client receives an error response (4xx or 5xx)

**Retry:**
- Client can retry the identical request
- Slot-level duplicate detection (ATT-02) ensures idempotency
- If the failure was transient (e.g., network timeout), the retry will succeed
- If the failure was due to invalid data (e.g., student not found), the retry will fail with the same error

**Verification:** Service-level unit tests verify that exceptions are thrown for invalid data, which would trigger transaction rollback in a real database.

### Scenario 2: Commit, Response Lost

**Behavior:**
- Bulk attendance is submitted and committed successfully
- Client loses the response (network timeout, client crash, etc.)
- Client retries the identical request

**Idempotency:**
- Slot-level duplicate detection (ATT-02 fix) checks for existing attendance at (student_id, timetable_slot_id, date) granularity
- For each student in the retry request:
  - If attendance already exists: student is added to `skippedStudentIds`, no new record created
  - If attendance doesn't exist: new record created, added to `createdCount`
- Response correctly reports already-existing records as skipped

**Verification:** ATT-01 tests verify that duplicate attendance is correctly detected and reported as skipped.

### At-Least-Once Delivery

**Actual behavior:** The system provides **at-least-once** request/retry semantics, not exactly-once:
- If the client doesn't receive a response, it cannot know if the request was committed
- Retry is safe: slot-level duplicate detection prevents duplicate records
- Response accurately reflects what happened: created vs. skipped counts

**Documentation:** The bulk attendance API is idempotent with respect to slot-level granularity. Clients can safely retry without creating duplicate records.

### ATT-06 Classification

**Status:** ✅ IMPLEMENTED BUT NOT FULLY VERIFIED

The retry behavior is correctly implemented:
- Transaction rollback prevents partial records
- Slot-level duplicate detection ensures idempotent retries
- Response accurately reports created vs. skipped records

**Limitation:** Full verification requires real database integration tests with transaction simulation, which is out of scope for R4.1. Service-level tests verify the logic but not the transaction behavior.

## API Compatibility Assessment

### Response Contract Change

**Before R4:** Bulk attendance returned `ResponseEntity.ok().build()` with no body  
**After R4:** Bulk attendance returns `ResponseEntity.ok(BulkAttendanceResponse)` with detailed summary

**Backward compatibility:**
- Clients expecting an empty response body will receive a JSON object instead
- This is a **breaking change** for clients that parse the response body
- However, the previous response had no body, so clients should not have been parsing it
- The change is additive: clients can now access detailed information that was previously unavailable

**Migration path:**
- Clients that ignore the response body: No change needed
- Clients that check for empty body: Need to update to handle the new response structure
- Clients that want to use the new information: Can access createdCount, skippedCount, skippedStudentIds

### Request Contract

**No change:** `BulkAttendanceRequest` structure remains the same  
**Validation:** `@Valid` annotation ensures request validation (timetableSlotId, date, attendance list)

### API Compatibility Classification

**Status:** ⚠️ BREAKING CHANGE — Response body added

The change is justified by the ATT-01 fix (bulk response lacks detail). Clients that were working around the missing information can now use the detailed response. Clients that ignored the response body are unaffected.
