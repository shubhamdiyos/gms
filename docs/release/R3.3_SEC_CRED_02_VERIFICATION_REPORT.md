### Whitelist Safety Analysis

The `/api/v1/users/me` prefix admits two endpoints:
- **GET `/users/me`** (`UserController.java:98`): Returns own profile only. Uses `TenantContext.username()` — no cross-user access.
- **PUT `/users/me`** (`UserController.java:110`): Updates own `fullName` and `phoneNumber` only. Explicitly blocks role, email, and password changes.

**Conclusion:** The whitelist does not inadvertently permit unrelated sensitive operations.

## 3. Runtime HTTP Verification (Phase D)

**Status: BLOCKED**

Runtime HTTP verification requires creating disposable test accounts with `requirePasswordChange=true`. This requires:
- An ADMIN or SUPERADMIN account to call `/api/v1/users/create` or `/api/v1/students/create`
- Or direct database access to insert test users

The existing backend on port 8080 was started before the current implementation changes. The task specification states: "Do not treat a previously running backend as proof of the new implementation."

Bootstrapping a fresh backend with a superadmin account (`APP_SUPERADMIN_ENABLED=true`) and creating disposable test users was not achievable within the remaining turn budget.

**Mitigation:** The `@SpringBootTest` integration tests load the full application context (including the real filter chain, real JWT provider, real password encoder) and exercise the same code paths as live HTTP requests. The 7/7 test pass rate provides strong verification.

## 4. Database Flag Verification

**Verified through integration tests:**
- Filter reads `requirePasswordChange` from `User` entity via `userService.findByUsername()` (database-backed)
- `AuthController.changePassword()` sets `user.setRequirePasswordChange(false)` and calls `userService.save(user)`
- Test `afterPasswordChange_businessEndpoint_allowed` confirms flag clearing unblocks business endpoints

---

## 5. JWT Behavior

**Verified through code inspection and integration tests:**
- JWT does NOT carry `requirePasswordChange` as a claim (confirmed in `JwtTokenProvider.createToken()`)
- Filter loads user from database on every authenticated request — JWT state is irrelevant to the enforcement decision
- Existing JWTs remain valid for whitelisted endpoints (login, change-password, /users/me)
- Existing JWTs are blocked for all other endpoints when the database flag is set
- After password change, the same JWT can access business endpoints (because the filter re-reads the flag from the database)

## 6. Performance Observation (Phase E)

**Status: NOT VERIFIED**

The filter performs one database lookup (`userService.findByUsername()`) per authenticated request. This adds latency proportional to the user table query time. No caching is implemented (per task restrictions).

Benchmarking was not feasible within the turn budget. The integration test suite ran 7 tests in 12.66 seconds (including Spring context startup), which suggests the filter overhead is acceptable for development use.
