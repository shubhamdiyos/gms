## Task A — Genuine Expired JWT Test

### Problem
The original `expiredJwt_rejected` test used a malformed token (`"invalid.jwt.token"`) with an invalid signature. This proved signature validation, not expiration validation.

### Solution
Added a helper method `createExpiredToken(String username)` that:
1. Uses reflection to access the private `key` field from `JwtTokenProvider`
2. Generates a correctly signed JWT using HS256 with the same signing key as the test `tokenProvider`
3. Sets the expiration timestamp 1 hour in the past (`now.minusSeconds(3600)`)
4. Sets the issued-at timestamp 2 hours in the past (`now.minusSeconds(7200)`)
5. Includes all required claims: `sub`, `roles`, `schoolId`, `empId`, `uid`, `iss`, `iat`, `exp`

The updated test:
- Submits the genuinely expired JWT to a protected endpoint (`/api/v1/users/me`)
- Asserts HTTP 401 (Unauthorized)
- Verifies `userService.findByUsername()` was never called (proving the request never reached business logic)

### Evidence
Test output shows the JWT was correctly parsed but rejected for expiration:
```
JWT parse/validate failed: JWT expired at 2026-11-03T06:52:22Z. Current time: 2026-11-03T07:52:22Z, 
a difference of 3600657 milliseconds. Allowed clock skew: 0 milliseconds.
```

**Result:** ✅ PASS — Expired JWT with valid signature is correctly rejected.

## Task B — Cross-User Password Change Test

### Problem
The original test asserted that User A's password should remain unchanged after attempting to change User B's password. This assertion was incorrect — the actual (correct) security behavior is:
- The endpoint uses `TenantContext.username()` from the JWT, not the `username` field in the request body
- User A's password WILL change if they authenticate successfully and provide the correct old password
- User B's password will NEVER change (the critical security property)

### Solution
Updated the test to:
1. Capture both `userA_originalPasswordHash` and `userB_originalPasswordHash` before the attack attempt
2. Mock `userService.save()` to echo back the updated User object (required for the endpoint to succeed)
3. Assert User B's password remains unchanged (critical security property)
4. Assert the response status is in (200, 400, 401, 403) — all acceptable outcomes
5. Conditionally assert User A's password:
   - If status == 200: User A's password changed (correct behavior — they authenticated and changed their own password)
   - If status == 4xx: User A's password unchanged (also acceptable — the attempt failed)

### Evidence
Test output shows the endpoint returned 200 (success) and changed User A's password:
```
MockHttpServletResponse:
   Status = 200
```

User B's password hash remained unchanged (critical security property verified).

**Result:** ✅ PASS — Cross-user attack correctly prevented; endpoint only operates on the authenticated user.

## Task C — Persistence Evidence Clarification

### Problem
The `afterPasswordChange_businessEndpoint_allowed` test uses `ArgumentCaptor` to verify the controller calls `userService.save()` with the correct updated User object. However, `UserService` and `UserDetailsService` are `@MockBean` (mocked), so the test does NOT prove real database transaction persistence.

### Solution
Added comprehensive JavaDoc to the test method:
```java
/**
 * SEC-CRED-02: Password change lifecycle verification with MOCKED persistence.
 *
 * <p>This test verifies the controller/filter integration: that the change-password endpoint
 * calls {@code userService.save()} with the correct updated User object (flag cleared, password
 * hashed). The {@code UserService} and {@code UserDetailsService} are {@code @MockBean} (lines
 * 50-54), so this test does NOT prove real database transaction persistence. The ArgumentCaptor
 * confirms the controller passed the correct object to the service layer, but the service is
 * mocked to echo back the same object without hitting a real database.</p>
 *
 * <p>For real database persistence verification, a separate integration test with Testcontainers
 * or an embedded database would be required (out of scope for SEC-CRED-02 test evidence).</p>
 */
```

### Classification
- **Test type:** Controller/filter integration test with mocked persistence
- **What it proves:** The controller calls `userService.save()` with the correct User object (flag cleared, password hashed)
- **What it does NOT prove:** Real database transaction persistence
- **Out of scope:** Testcontainers or embedded database tests (not required for SEC-CRED-02)

**Result:** ✅ DOCUMENTED — Mocked persistence clearly described; no false claims about database transactions.
