## 3. Explanation of Failed Upsert Experiment

### 3.1 R4.5 Hypothesis

R4.5 attempted to fix the concurrency defect using PostgreSQL's atomic upsert:
```sql
INSERT INTO attendances (...)
VALUES (...)
ON CONFLICT (student_id, timetable_slot_id, date) DO NOTHING
```

**Expected behavior:** Exactly one record persists when multiple threads attempt concurrent inserts.

**Actual behavior:** Zero records persisted in concurrency test.

### 3.2 Root Cause Analysis

**The concurrency test itself has a design flaw:**

```java
// Test setup (line 365-367)
try (MockedStatic<TenantContext> tenantContext = mockStatic(TenantContext.class)) {
    tenantContext.when(TenantContext::employeeId).thenReturn(teacherEmployee.getId());
    tenantContext.when(TenantContext::schoolId).thenReturn(school1.getId());
    
    // Worker threads (lines 379-401)
    for (int t = 0; t < threadCount; t++) {
        executor.submit(() -> {
            latch.await();
            // ... call attendanceService.recordBulkAttendance(request) ...
        });
    }
}
```

**Problem:** `MockedStatic<TenantContext>` is **thread-local**. The mock is set up in the main test thread but is NOT visible to worker threads in the ExecutorService.

**Execution flow:**
1. Main thread sets up TenantContext mock
2. Main thread submits 5 worker tasks to ExecutorService
3. Worker threads execute `attendanceService.recordBulkAttendance(request)`
4. Service method checks `TenantContext.employeeId()` (line 110 in restored code)
5. **Worker threads see NULL** (mock not visible)
6. Service returns `ResponseEntity.badRequest().build()` immediately (line 111)
7. No database operations occur
8. Result: 0 records persisted

**Why all R4.5 fix attempts failed:**
- The upsert approach was technically correct
- But the test never reached the upsert code
- All threads returned 400 before executing any database operations
- The "0 records" result was consistent across all attempts because the root cause (thread-local mock) was never addressed

### 3.3 Why Other Tests Pass

**Non-concurrent tests** (e.g., `allValidBulkSubmission_commitsAllRecords`):
- Execute in the main test thread
- MockedStatic is visible
- TenantContext returns mocked values
- Service executes normally
- Tests pass

**Concurrent test** (`concurrentSubmissions_respectUniqueConstraint`):
- Executes in worker threads
- MockedStatic is NOT visible
- TenantContext returns null
- Service returns 400 immediately
- Test fails with "Expected size: 1 but was: 0"

### 3.4 Corrective Options (Not Implemented in R4.6)

**Option 1: Fix the test**
- Set up MockedStatic inside each worker thread
- Or use a different approach to propagate TenantContext to worker threads
- Pros: Test would accurately verify concurrency behavior
- Cons: Doesn't fix the underlying concurrency defect in the application

**Option 2: Accept the defect**
- Document the concurrency defect as OPEN
- Create separate architectural task to address it
- Pros: Honest assessment, avoids false confidence
- Cons: Defect remains in production code

**R4.6 Decision:** Option 2 — Document as OPEN, defer to separate task

## 4. Restored Implementation Details

### 4.1 AttendanceServiceImpl.recordBulkAttendance()

**Restored to R4.4 pattern with R4.2 fixes:**

```java
@Override
@Transactional
public ResponseEntity<?> recordBulkAttendance(BulkAttendanceRequest request) {
    if (TenantContext.employeeId() == null || TenantContext.schoolId() == null) {
        return ResponseEntity.badRequest().build();
    }

    // One slot for the whole class register, read with the tenant in the query.
    TimetableSlot timetableSlot = timetableSlotRepository
            .findByIdAndSchool_Id(request.getTimetableSlotId(), TenantContext.schoolId())
            .orElseThrow(() -> new NotFoundException("TIMETABLE_SLOT_NOT_FOUND",
                    "Timetable slot not found for the current school"));

    School school = schoolRepository.getReferenceById(TenantContext.schoolId());

    // ATT-06 fix: validate ALL students before writing ANY records.
    Integer expectedClassroomId = timetableSlot.getTimetable().getClassroom().getId();
    List<Student> validatedStudents = new java.util.ArrayList<>();
    for (var item : request.getAttendance()) {
        Student student = studentRepository.findById(item.getStudentId())
                .orElseThrow(() -> new NotFoundException("STUDENT_NOT_FOUND", "Student not found"));

        if (!student.getClassroomId().equals(expectedClassroomId)) {
            throw new IllegalArgumentException(
                    "Student " + student.getId() + " does not belong to the classroom for this timetable slot");
        }

        validatedStudents.add(student);
    }

    int createdCount = 0;
    java.util.List<Integer> skippedStudentIds = new java.util.ArrayList<>();

    for (int i = 0; i < request.getAttendance().size(); i++) {
        var item = request.getAttendance().get(i);
        Student student = validatedStudents.get(i);

        // ATT-02: Check if attendance already exists
        boolean attendanceExists = attendanceRepository.existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate(
                TenantContext.schoolId(), item.getStudentId(), request.getTimetableSlotId(), request.getDate());

        if (!attendanceExists) {
            Attendance attendance = new Attendance();
            attendance.setSchool(school);
            attendance.setStudent(student);
            attendance.setTimetableSlot(timetableSlot);
            attendance.setDate(request.getDate());
            attendance.setStatus(item.getStatus());
            attendance.setRemarks(item.getRemarks());

            // Set creator/updated by
            User creator = userService.findByEmployee_Id()
                    .orElseThrow(() -> new EntityNotFoundException("Creator user not found"));
            attendance.setCreatedBy(creator);
            attendance.setUpdatedBy(creator);

            attendanceRepository.save(attendance);
            createdCount++;
        } else {
            skippedStudentIds.add(item.getStudentId());
        }
    }

    // ATT-01: Return detailed summary
    com.gms.model.response.BulkAttendanceResponse response = new com.gms.model.response.BulkAttendanceResponse();
    response.setTotalStudents(request.getAttendance().size());
    response.setCreatedCount(createdCount);
    response.setSkippedCount(skippedStudentIds.size());
    response.setSkippedStudentIds(skippedStudentIds);
    response.setMessage(String.format("Attendance recorded for %d students, %d skipped (already exists)",
            createdCount, skippedStudentIds.size()));

    return ResponseEntity.ok(response);
}
```

**Key characteristics:**
- `@Transactional` annotation restored (declarative transaction management)
- Validate-all-before-write pattern preserved (R4.2)
- Standard `attendanceRepository.save()` used (not native upsert)
- BulkAttendanceResponse contract preserved (ATT-01)
- Slot-level duplicate detection preserved (ATT-02)

## 7. Remaining Concurrency Defect

### 7.1 Defect Classification

**Status:** OPEN  
**Severity:** Medium  
**Impact:** Concurrent duplicate attendance submissions may result in race conditions  
**Component:** AttendanceServiceImpl.recordBulkAttendance()

### 7.2 Defect Description

The current implementation uses a check-then-act pattern for duplicate detection:

```java
boolean attendanceExists = attendanceRepository.existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate(...);

if (!attendanceExists) {
    Attendance attendance = new Attendance();
    // ... set fields ...
    attendanceRepository.save(attendance);
}
```

**Race condition scenario:**
1. Thread A checks `existsBy...` → returns `false`
2. Thread B checks `existsBy...` → returns `false` (before A commits)
3. Thread A attempts INSERT → succeeds
4. Thread B attempts INSERT → violates unique constraint `uq_attendance_student_slot_date`
5. `DataIntegrityViolationException` thrown
6. `@Transactional` marks transaction for rollback
7. Result: Both threads fail, 0 records persisted

### 7.3 Evidence

**Test:** `AttendancePostgresIntegrationTest.concurrentSubmissions_respectUniqueConstraint`  
**Expected:** Exactly 1 record persists after 5 concurrent submissions  
**Actual:** 0 records persist  
**Root cause:** Thread-local MockedStatic issue (see Section 3.2)

**Note:** The test failure is currently masked by the test design flaw. Once the test is fixed to properly propagate TenantContext to worker threads, the underlying concurrency defect will be exposed.

### 7.4 Remediation Options

**Option 1: Database-level locking**
```java
// Use SELECT ... FOR UPDATE to lock the row before checking
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Attendance a WHERE ...")
Optional<Attendance> findByStudentAndSlotAndDateForUpdate(...);
```
- Pros: Prevents race condition at database level
- Cons: Requires additional query, may impact performance

**Option 2: Catch and handle DataIntegrityViolationException**
```java
try {
    attendanceRepository.save(attendance);
} catch (DataIntegrityViolationException e) {
    if (e.getMessage().contains("uq_attendance_student_slot_date")) {
        // Duplicate detected, skip
        skippedStudentIds.add(item.getStudentId());
    } else {
        throw e;
    }
}
```
- Pros: Simple, handles race condition gracefully
- Cons: Exception-driven control flow, transaction may be marked for rollback

**Option 3: Atomic upsert (R4.5 approach)**
```java
int rowsInserted = attendanceRepository.insertIgnoreDuplicate(...);
```
- Pros: Atomic, no race condition
- Cons: Requires native query, R4.5 implementation had issues

**Option 4: Accept the defect**
- Document as known limitation
- Rely on client-side retry logic
- Pros: No code changes required
- Cons: Poor user experience under concurrent load

**Recommendation:** Option 2 (catch and handle) or Option 3 (atomic upsert with proper transaction management)

### 7.5 Scope Decision

**This defect is NOT fixed in R4.6.**

**Rationale:**
1. R4.6 scope is to isolate R4.5 experimental changes and restore stability
2. Concurrency fix requires architectural decisions beyond R4.6 scope
3. Test design flaw must be fixed first to properly verify any fix
4. Defect is properly documented and classified as OPEN

**Next steps:**
1. Fix the concurrency test design (thread-local mock issue)
2. Create separate task (R7 or similar) to address the concurrency defect
3. Evaluate remediation options with proper test coverage
4. Implement and verify the fix
