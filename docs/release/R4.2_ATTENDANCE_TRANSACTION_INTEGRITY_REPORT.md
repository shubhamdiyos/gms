## 1. Original Transaction Behavior

`AttendanceServiceImpl.recordBulkAttendance()` was annotated `@Transactional` but contained a code path that returned `ResponseEntity.badRequest().build()` from inside the student processing loop — **after** earlier iterations had already called `attendanceRepository.save()`.

Spring's `@Transactional` only triggers automatic rollback on **unchecked exceptions** (subclasses of `RuntimeException`). A normal method return, including an HTTP 400 response, does **not** cause rollback. The transaction commits normally with whatever records were persisted before the return.

## 2. All Exit Paths (Before Fix)

| Line | Exit Path | Type | Saves Before? | Rollback? |
|------|-----------|------|---------------|-----------|
| 107-109 | TenantContext null | Normal return (400) | No | N/A (safe) |
| 112-115 | TimetableSlot not found | `NotFoundException` (unchecked) | No | YES (safe) |
| 123-124 | Student not found | `NotFoundException` (unchecked) | Maybe (earlier students) | YES |
| **126-128** | **Classroom mismatch** | **Normal return (400)** | **YES (earlier students)** | **NO — DEFECT** |
| 145-146 | User not found | `EntityNotFoundException` (unchecked) | Maybe | YES |

**The defect:** Line 126-128. When student C has a classroom mismatch after students A and B were already saved, the method returns 400 but the transaction COMMITS A and B's records.

## 3. Partial Commit Reproduction

**Test:** `BulkAttendanceAtomicityDefectTest.classroomMismatch_afterValidStudents_saveCalledForEarlierStudents`

**Setup:** 3 students — A (classroom 100), B (classroom 100), C (classroom 200). Slot belongs to classroom 100.

**Result (before fix):**
- `attendanceRepository.save()` called **2 times** (for A and B)
- Method returns HTTP 400
- In production: A and B's records would be **committed** despite the overall request failing

## 4. Root Cause

The implementation interleaved validation and persistence in a single loop. The classroom mismatch check (`return ResponseEntity.badRequest().build()`) was a normal return, not an exception. Spring `@Transactional` does not rollback on normal returns.

## 5. Remediation

**Approach:** Validate-all-before-write.

The method now performs two passes:
1. **Validation pass:** Iterate all students, verify existence and classroom membership. Throws `NotFoundException` (missing student) or `IllegalArgumentException` (classroom mismatch) — both unchecked exceptions that trigger `@Transactional` rollback.
2. **Write pass:** Only reached if all validations pass. Performs duplicate detection and saves.

**HTTP contract preserved:**
- `NotFoundException` → 404 (via `GlobalExceptionHandler`)
- `IllegalArgumentException` → 400 (via `GlobalExceptionHandler`) — same status as the original `return ResponseEntity.badRequest().build()`

**Code change in `AttendanceServiceImpl.recordBulkAttendance()`:**
```java
// Validation pass — no writes, all exceptions trigger rollback
Integer expectedClassroomId = timetableSlot.getTimetable().getClassroom().getId();
List<Student> validatedStudents = new java.util.ArrayList<>();
for (var item : request.getAttendance()) {
    Student student = studentRepository.findById(item.getStudentId())
            .orElseThrow(() -> new NotFoundException("STUDENT_NOT_FOUND", "Student not found"));
    if (!student.getClassroomId().equals(expectedClassroomId)) {
        throw new IllegalArgumentException(
                "Student " + student.getId() + " does not belong to the classroom for this timetable slot");
    }
    validatedStudents.add(student);
}

// Write pass — only reached if all validations pass
for (int i = 0; i < request.getAttendance().size(); i++) {
    // ... duplicate detection and save logic unchanged
}
```

## 10. Remaining Limitations

1. **Database-backed verification BLOCKED** — No Testcontainers infrastructure available. Mocked tests prove the mechanism (exceptions before writes) but cannot prove actual PostgreSQL transaction rollback. This requires task #62 (Testcontainers isolation) to be completed.

2. **`@Transactional` on the service method** — The fix ensures all validation failures throw unchecked exceptions before any writes. However, the `@Transactional` proxy only works when the method is called through the Spring bean proxy (not from within the same class). This is the standard Spring limitation and is not a concern for controller→service calls.

3. **Pre-existing integration test failures** — `PasswordChangeEnforcementFilterTest` (10 tests) fails due to missing database context. This is unrelated to the attendance changes.

4. **No load/concurrency testing** — The concurrent duplicate submission scenario is documented but not load-tested. The database unique constraint `uq_attendance_student_slot_date` provides the safety net.
