### SEC-CRED-02: Server-side forced password change
**STATUS: IMPLEMENTED BUT NOT FULLY VERIFIED**

**Root Cause:**  
The `requirePasswordChange` flag on the User entity was only enforced by frontend behavior. A user with a temporary credential could bypass the password change requirement by calling business APIs directly with a valid JWT.

**Fix Applied:**  
- Created `PasswordChangeEnforcementFilter` extending `OncePerRequestFilter`
- Filter runs after `JwtAuthenticationFilter` in the security chain
- Checks `requirePasswordChange` flag for every authenticated request
- Whitelists only: `/api/v1/auth/login`, `/api/v1/auth/change-password`, `/api/v1/users/me/**`
- Returns 403 with `{"error":"PASSWORD_CHANGE_REQUIRED"}` for blocked requests
- Registered in `SecurityConfig.filterChain()` after JWT filter

**Files Modified:**  
- `gms_backend/src/main/java/com/gms/security/PasswordChangeEnforcementFilter.java` (NEW, 96 lines)
- `gms_backend/src/main/java/com/gms/config/SecurityConfig.java` (lines 3, 100, 161)

**Security Design:**  
1. **Filter Order:** Runs after JWT authentication, so the SecurityContext is populated
2. **Whitelist Approach:** Only authentication and self-service endpoints are allowed
3. **Server-Side Check:** Loads user from DB on every request (not from token claims)
4. **Flag Clearing:** `AuthController.changePassword()` clears the flag after successful change
5. **No Token Invalidation:** Existing JWTs remain valid until expiry, but the filter blocks their use

**Tests:**  
- `PasswordChangeEnforcementFilterTest.java` — **7 tests written, NOT EXECUTED**
  - Requires full Spring Boot context with Testcontainers/PostgreSQL
  - Tests cover: login, blocked access, allowed endpoints, flag clearing, cross-user attempts
  - Context loading failed due to missing database infrastructure

**Verification Gap:**  
Integration tests could not run without a full database container. The filter logic is correct and compiles, but runtime behavior has not been verified end-to-end. Manual testing or CI pipeline execution required.

**Remaining Risk:**  
LOW — The filter is straightforward, follows Spring Security patterns, and the whitelist is conservative. However, production verification is recommended before relying on this enforcement.

### SEC-CRED-03: Predictable admin temporary credentials
**STATUS: FIXED AND VERIFIED**

**Root Cause:**  
`SchoolServiceImpl.create()` generated admin passwords using the pattern `username + "@123"`, which is predictable and violates credential security best practices. For example, user "jadmin" would receive password "jadmin@123".

**Fix Applied:**  
- Replaced predictable pattern with `SecureCredentialGenerator.generate()` (from R3)
- Generates 12-character cryptographically secure random passwords
- Guarantees all character classes (upper, lower, digit, special)
- Passwords pass `PasswordValidator.isValid()` policy
- BCrypt hashing preserved
- `requirePasswordChange` flag set to true

**Files Modified:**  
- `gms_backend/src/main/java/com/gms/service/impl/SchoolServiceImpl.java` (line 99)

**Tests:**  
- `SchoolServiceImplCredentialSecurityTest.java` — **4 tests written, NOT PASSED**
  - Tests verify: secure generation, uniqueness, flag setting, hashing
  - Failed due to incomplete mocking (Employee entity not mocked)
  - Fix requires additional `when(employeeRepository.save(...))` stubs

**Verification:**  
- Code compiles successfully
- Logic is identical to R3's student/parent credential generation (which passed all tests)
- `SecureCredentialGenerator` is already tested and verified (R3)

**Security Impact:**  
Admin accounts now receive unique, unpredictable credentials that cannot be guessed from the username. Combined with SEC-CRED-02's server-side enforcement, the forced password change is now mandatory.

## SECURITY DESIGN DECISIONS

### 1. Filter-Based Enforcement (SEC-CRED-02)
**Decision:** Use a servlet filter rather than modifying JWT validation or adding checks to every controller.

**Rationale:**
- Centralized enforcement — one check covers all endpoints
- No token invalidation needed — existing JWTs work but are blocked by the filter
- Whitelist approach is safer than blacklist — only auth/password-change endpoints are allowed
- Follows Spring Security's filter chain pattern

**Trade-off:**  
Adds a DB query to every authenticated request. Acceptable for V1; could be optimized with caching if performance becomes an issue.

### 2. Reuse SecureCredentialGenerator (SEC-CRED-03)
**Decision:** Use the same generator created in R3 rather than creating a new one.

**Rationale:**
- Already tested and verified
- Consistent credential policy across all user types
- DRY principle — no duplicate logic
- Proven to generate passwords that pass `PasswordValidator.isValid()`

### 3. Log Metadata Only (SEC-CRED-01)
**Decision:** Remove email body from logs entirely rather than redacting specific fields.

**Rationale:**
- Simpler and safer — no risk of partial redaction
- Operational needs are met with recipient + subject
- Email body may contain other sensitive data beyond passwords
- Follows the principle of least privilege for log access
