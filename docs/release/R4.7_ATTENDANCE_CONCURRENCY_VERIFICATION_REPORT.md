## 1. Test Harness Changes

### 1.1 Problem Identified in R4.6

The concurrency test (`concurrentSubmissions_respectUniqueConstraint`) used `MockedStatic<TenantContext>` in the main test thread:

```java
// R4.5/R4.6 implementation (DEFECTIVE)
try (MockedStatic<TenantContext> tenantContext = mockStatic(TenantContext.class)) {
    tenantContext.when(TenantContext::employeeId).thenReturn(teacherEmployee.getId());
    tenantContext.when(TenantContext::schoolId).thenReturn(school1.getId());
    
    // Worker threads submitted to ExecutorService
    for (int t = 0; t < threadCount; t++) {
        executor.submit(() -> {
            // Worker threads CANNOT see the MockedStatic
            // TenantContext.employeeId() returns NULL
            // Service returns 400 immediately
            // No database operations occur
        });
    }
}
```

**Root Cause:** `TenantContext` uses `ThreadLocal<Principal>` (line 22 in TenantContext.java). ThreadLocal values are thread-specific and not shared across threads. `MockedStatic` from Mockito is also thread-local to the thread that created the mock.

**Result:** All 5 worker threads received `null` from `TenantContext.employeeId()` and `TenantContext.schoolId()`, causing the service to return HTTP 400 immediately without executing any database operations. The test showed "0 records persisted" not because of a concurrency defect, but because no records were ever attempted.

### 1.2 Solution Implemented in R4.7

Establish `TenantContext` independently inside each worker thread:

```java
// R4.7 implementation (CORRECTED)
for (int t = 0; t < threadCount; t++) {
    executor.submit(() -> {
        try {
            latch.await();
            
            // R4.7: Set up TenantContext for this worker thread
            TenantContext.set(new TenantContext.Principal(
                    teacher.getUsername(),
                    teacher.getId(),
                    school1.getId(),
                    teacherEmployee.getId(),
                    Set.of("TEACHER")
            ));
            
            // Now the worker thread has valid tenant context
            ResponseEntity<?> response = attendanceService.recordBulkAttendance(request);
            // ... track response ...
        } finally {
            // R4.7: Clear TenantContext to prevent thread pollution
            TenantContext.clear();
            completionLatch.countDown();
        }
    });
}
```

**Key Changes:**
1. Removed `MockedStatic<TenantContext>` wrapper
2. Each worker thread calls `TenantContext.set()` with a valid `Principal`
3. Each worker thread calls `TenantContext.clear()` in finally block
4. Added tracking for HTTP 400 responses to detect context failures
5. Updated test name from `R4.5-02` to `R4.7-01` to reflect the correction

## 9. Remaining Confirmed Defects

### 9.1 Concurrency Race Condition — CONFIRMED

**Status:** CONFIRMED  
**Severity:** Medium  
**Component:** `AttendanceServiceImpl.recordBulkAttendance()`  
**Lines:** 148-160 (check-then-act pattern)

**Defect Description:**

The implementation uses a check-then-act pattern for duplicate detection:

```java
// Line 148-150: Check
boolean attendanceExists = attendanceRepository.existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate(
        TenantContext.schoolId(), item.getStudentId(), request.getTimetableSlotId(), request.getDate());

// Line 152-160: Act
if (!attendanceExists) {
    Attendance attendance = new Attendance();
    // ... set fields ...
    attendanceRepository.save(attendance);
    createdCount++;
} else {
    skippedStudentIds.add(item.getStudentId());
}
```

**Race Condition:**
1. Thread A checks `existsBy...` → returns `false`
2. Thread B checks `existsBy...` → returns `false` (before A commits)
3. Thread A attempts INSERT → succeeds
4. Thread B attempts INSERT → violates unique constraint
5. `DataIntegrityViolationException` thrown
6. Transaction rolls back
7. Client receives error instead of success/skipped response

**Impact:**
- Under concurrent load, clients receive HTTP 500 errors (unhandled exception) or transaction rollbacks
- Legitimate attendance submissions fail
- Poor user experience under concurrent access patterns

**Evidence:**
- R4.7 concurrency test: 4 out of 5 threads received DataIntegrityViolationException
- SQL error logs: `duplicate key value violates unique constraint "uq_attendance_student_slot_date"`
- Database state: Exactly 1 record persisted (constraint enforced, but 4 transactions failed)

### 9.2 Smallest Viable Remediation Options

**Option 1: Catch and Handle DataIntegrityViolationException**

```java
try {
    attendanceRepository.save(attendance);
    createdCount++;
} catch (DataIntegrityViolationException e) {
    if (e.getMessage().contains("uq_attendance_student_slot_date")) {
        // Duplicate detected at database level, treat as skipped
        skippedStudentIds.add(item.getStudentId());
    } else {
        throw e; // Re-throw unexpected exceptions
    }
}
```

**Pros:**
- Minimal code change
- Handles race condition gracefully
- Returns HTTP 200 with accurate created/skipped counts
- No architectural changes required

**Cons:**
- Exception-driven control flow (not ideal but acceptable for race conditions)
- Transaction may be marked for rollback (need to verify Spring behavior)

**Option 2: Atomic Upsert (INSERT ... ON CONFLICT DO NOTHING)**

```java
@Modifying
@Query(value = """
    INSERT INTO attendances (school_id, student_id, timetable_slot_id, date, status, remarks, deleted, created_by, updated_by, created_at, updated_at)
    VALUES (:schoolId, :studentId, :timetableSlotId, :date, :status, :remarks, false, :createdBy, :updatedBy, NOW(), NOW())
    ON CONFLICT (student_id, timetable_slot_id, date) DO NOTHING
    """, nativeQuery = true)
int insertIgnoreDuplicate(...);
```

**Pros:**
- Atomic operation (no race condition)
- No exception handling needed
- Returns count of inserted rows (0 if duplicate, 1 if inserted)

**Cons:**
- Requires native SQL query
- R4.5 attempted this but had transaction management issues
- May require removing `@Transactional` from service method

**Option 3: Pessimistic Locking (SELECT ... FOR UPDATE)**

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Attendance a WHERE a.student.id = :studentId AND a.timetableSlot.id = :slotId AND a.date = :date")
Optional<Attendance> findByStudentAndSlotAndDateForUpdate(...);
```

**Pros:**
- Prevents race condition at database level
- Standard JPA approach

**Cons:**
- Requires additional query before INSERT
- May impact performance under high concurrency
- Lock contention possible

**Recommendation:** Option 1 (catch and handle) is the smallest viable change that addresses the defect without architectural modifications.
