## 2. Concurrency Testing (R4.5-2)

### Test Implementation
**File:** `AttendancePostgresIntegrationTest.concurrentSubmissions_respectUniqueConstraint`

**Test Design:**
- 5 threads submit identical attendance requests concurrently
- Each thread calls `attendanceService.recordBulkAttendance(request)`
- Assertion: Exactly 1 database record must exist after all threads complete
- Capture: All thread responses and exceptions

### Test Results

**Before Fix Attempts:**
```
Expected size: 1 but was: 0
```
All 5 threads failed — 0 records persisted.

### Root Cause Analysis

The application has a **genuine concurrency defect** in the check-then-act pattern:

```java
// Current implementation (DEFECTIVE)
boolean attendanceExists = attendanceRepository.existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate(...);

if (!attendanceExists) {
    Attendance attendance = new Attendance();
    // ... set fields ...
    attendanceRepository.save(attendance);
}
```

**Race Condition:**
1. Thread A checks `existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate` → returns `false`
2. Thread B checks `existsByStudent_School_IdAndStudent_IdAndTimetableSlot_IdAndDate` → returns `false` (before A commits)
3. Thread A attempts INSERT → succeeds
4. Thread B attempts INSERT → violates unique constraint `uq_attendance_student_slot_date`
5. `DataIntegrityViolationException` is thrown
6. `@Transactional` marks the entire transaction for rollback
7. Even if caught, the transaction is poisoned — all work in that transaction is rolled back
8. Result: 0 records persisted

### Fix Attempts

**Attempt 1: Try-Catch with Flush**
```java
try {
    attendanceRepository.save(attendance);
    attendanceRepository.flush();
    createdCount++;
} catch (DataIntegrityViolationException e) {
    if (e.getMessage().contains("uq_attendance_student_slot_date")) {
        skippedStudentIds.add(item.getStudentId());
    } else {
        throw e;
    }
}
```
**Result:** FAILED — Exception inside `@Transactional` marks transaction for rollback regardless of catch block.

**Attempt 2: REQUIRES_NEW Transaction Propagation**
```java
DefaultTransactionDefinition requiresNewDef = new DefaultTransactionDefinition();
requiresNewDef.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
TransactionTemplate requiresNewTx = new TransactionTemplate(
    transactionTemplate.getTransactionManager(), requiresNewDef);

Boolean saved = requiresNewTx.execute(status -> {
    // ... save logic ...
});
```
**Result:** FAILED — Still 0 records persisted. The outer `@Transactional` transaction is still affected by the inner transaction's exception.

**Attempt 3: Atomic Upsert (INSERT ... ON CONFLICT DO NOTHING)**
```java
// Repository method
@Modifying
@Transactional
@Query(value = """
    INSERT INTO attendances (school_id, student_id, timetable_slot_id, date, status, remarks, deleted, created_by, updated_by, created_at, updated_at)
    VALUES (:schoolId, :studentId, :timetableSlotId, :date, :status, :remarks, false, :createdBy, :updatedBy, NOW(), NOW())
    ON CONFLICT (student_id, timetable_slot_id, date) DO NOTHING
    """, nativeQuery = true)
int insertIgnoreDuplicate(...);
```
**Result:** FAILED — Still 0 records persisted. Multiple variations tested:
- With @Transactional on service method
- Without @Transactional on service method (programmatic transaction management)
- With @Transactional on repository method
- All combinations failed with same result

**Attempt 4: Programmatic Transaction Management**
Removed `@Transactional` from `recordBulkAttendance` method and wrapped entire logic in `transactionTemplate.execute()`.
**Result:** FAILED — No change in behavior, still 0 records persisted.

### Root Cause Analysis (Updated)

The concurrency defect persists across all fix attempts because of fundamental Spring transaction management behavior:

1. **@Transactional interference**: Even with programmatic transaction management, the transaction context affects how native queries execute
2. **Exception propagation**: DataIntegrityViolationException marks transactions for rollback at the infrastructure level, before application code can catch it
3. **Native query transaction requirements**: @Modifying queries require explicit transaction boundaries that interact poorly with concurrent execution

The defect requires architectural changes beyond "smallest safe correction within attendance scope":
- Redesign the entire attendance recording flow with explicit transaction boundaries per-student
- Or: Implement database-level locking (SELECT ... FOR UPDATE) before the check
- Or: Use a message queue for asynchronous, serialized processing
- Or: Accept the defect and document it as a known limitation

**Scope Decision:** This defect is documented but NOT fixed in R4.5. All attempted fixes failed. A separate architectural task (R6 or similar) is required.
